**1. Introduction & Goal**

This project aims to implement an efficient training pipeline for two distinct Large Language Models (LLMs), designated `model_a` and `model_b`. The key characteristics of this pipeline are:

1.  **Sequential Dependency:** `model_b`'s generation process is conditioned on both an initial prompt *and* the output generated by `model_a` from the same prompt.
2.  **Disjoint Training:** While sequentially dependent for generation, the models are trained with separate optimizers and potentially different DeepSpeed/FSDP configurations. Their gradients are not shared during the backward pass for their respective losses.
3.  **Distributed Training:** The training process must scale across multiple GPUs, potentially spanning multiple nodes, leveraging the `accelerate` library and backend frameworks like DeepSpeed.
4.  **Accelerated Inference:** To mitigate the bottleneck of generating intermediate sequences during training (especially from potentially large models), inference for both `model_a` and `model_b` will be offloaded to dedicated GPU resources running highly optimized vLLM servers.

The ultimate goal is to create a robust and scalable framework suitable for advanced RL training schemes (like GRPO or PPO variants) or other methods requiring fast generation interleaved with gradient updates on separate models.

**2. Problem Statement**

Standard training frameworks like Hugging Face `Trainer` are primarily designed for single-model training or tightly coupled multi-model scenarios (e.g., encoder-decoder). They do not natively support:

*   Orchestrating separate distributed training configurations (like distinct DeepSpeed engines) for multiple models within the same training script.
*   Integrating external, high-throughput inference servers (like vLLM) for intermediate generation steps within the training loop.
*   Managing the specific GPU resource allocation required for separating inference servers from training workers.

Therefore, a custom solution is required to manage the complex interplay between distributed training, sequential generation, and inference offloading.

**3. Chosen Architecture**

After evaluating alternatives (like heavy modification of `Trainer`), the chosen architecture relies on a **custom training loop built directly on the `accelerate` library**, combined with **multiple standalone vLLM server instances**.

*   **Custom Training Loop (`DisjointSequentialTrainer` Class):** Provides maximum flexibility to manage the unique requirements. It avoids the constraints and bloat of the standard `Trainer`.
*   **`accelerate` Library:** Handles the complexities of distributed training setup (launching processes, device placement), mixed precision, gradient accumulation, and integration with backends like DeepSpeed.
*   **Two `Accelerator` Instances:** Following `accelerate` documentation for disjoint DeepSpeed models, two `Accelerator` instances (`accelerator_a`, `accelerator_b`) are created. They share the underlying `AcceleratorState` (including knowledge of both DeepSpeed plugins) but allow for separate `backward` calls managed by potentially different DeepSpeed engines. This is crucial because the backward passes for `model_a` and `model_b` happen independently based on their respective losses.
*   **Multiple vLLM Servers:** Instead of modifying the vLLM server code, separate instances are launched for `model_a` and `model_b`, each pinned to specific GPUs using `CUDA_VISIBLE_DEVICES`. This aligns with the standard vLLM server design and simplifies resource management and weight synchronization.
*   **`VLLMClient`:** A client class (adapted from `trl`) is used within the main training process to communicate with the vLLM servers via HTTP requests for generation tasks. Separate clients connect to the respective servers for `model_a` and `model_b`.
*   **GPU Allocation Strategy (Example: N=1, G=8):**
    *   GPU 0: Dedicated to vLLM server for `model_a`.
    *   GPU 1: Dedicated to vLLM server for `model_b`. (A placeholder RM/Verifier model might also target this GPU later, requiring careful memory management).
    *   GPUs 2-7: Used by `accelerate` for distributed training of `model_a` and `model_b`.
*   **Weight Synchronization:** A mechanism (`_move_model_to_vllm`) is included to periodically update the weights of the vLLM inference servers with the latest weights from the training models, ensuring inference reflects training progress. This is handled only by the main training process.

**4. Implementation Details**

The core logic is encapsulated within the `DisjointSequentialTrainer` class.

**4.1. Argument Parsing (`ScriptArguments`)**

A `dataclass` (`ScriptArguments`) defines all necessary command-line arguments, including:
*   Paths for `model_a`, `model_b`, and their respective DeepSpeed JSON configuration files (`ds_config_a`, `ds_config_b`).
*   Paths for data files and the output directory.
*   Training hyperparameters (batch sizes, epochs/steps, learning rates, scheduler type, warmup, weight decay, gradient accumulation, gradient clipping norms - potentially separate for A and B).
*   vLLM server connection details (`vllm_host_a`, `vllm_port_a`, `vllm_host_b`, `vllm_port_b`, `vllm_server_timeout`).
*   vLLM generation parameters (`vllm_max_new_tokens`, `vllm_temperature`, etc.).
*   Standard options like `seed`, `logging_steps`, `save_steps`, `eval_steps`, `resume_from_checkpoint`, `mixed_precision`.

**4.2. Initialization (`__init__`)**

The constructor orchestrates the setup:
1.  Stores arguments (`args`).
2.  Initializes state variables (`global_step`, `current_epoch`).
3.  Sets up logging and random seeds (`_setup_logging`, `set_seed`).
4.  **Initializes Accelerators (`_initialize_accelerators`):**
    *   Creates `DeepSpeedPlugin` instances for A and B.
    *   Stores them in a dictionary `deepspeed_plugins`.
    *   Creates `accelerator_a = Accelerator(deepspeed_plugin=deepspeed_plugins, ...)` which initializes the shared state.
    *   Creates `accelerator_b = Accelerator()` which inherits the shared state.
    *   Stores both in `self.accelerators`. `self.accelerator` is set to `accelerator_a` for convenience in accessing shared state properties like device or rank.
    *   Logs GPU visibility info for debugging `CUDA_VISIBLE_DEVICES`.
5.  **Initializes vLLM Clients:** *Only on the main process* (`self.accelerator.is_main_process`), creates `VLLMClient` instances (`self.vllm_client_a`, `self.vllm_client_b`) connecting to the specified server addresses and ports. Includes connection checks and error handling.
6.  Loads tokenizer, training models (`model_a`, `model_b`), datasets, and optimizers using helper methods.
7.  Calculates the total number of training steps (`_calculate_num_training_steps`).
8.  Creates learning rate schedulers now that the total steps are known (`_create_schedulers`).
9.  **Prepares Components (`_prepare_components`, `_prepare_schedulers`):** Critically uses `accelerator.state.select_deepspeed_plugin()` to set the active context before calling `accelerators[key].prepare()` for each model, its optimizer, the dataloaders, and the schedulers. This ensures correct wrapping (DDP/DeepSpeed/FSDP) and device placement according to the respective configurations.
10. Loads training state from a checkpoint if `args.resume_from_checkpoint` is provided (`load_checkpoint`).

**4.3. Training Loop (`train`, `_training_step`)**

*   The `train` method contains the outer loop (epochs) and inner loop (batches).
*   The `_training_step` method encapsulates the logic for one batch:
    1.  **vLLM Generation (Main Process):** Decodes prompts from the batch, sends requests to `vllm_client_a` and `vllm_client_b` sequentially (constructing prompts for B using A's output). Stores generated token IDs.
    2.  **Broadcast (Optional but likely needed):** Uses `accelerator.broadcast_object_list` to send the generated token IDs from the main process to all other training ranks.
    3.  **Loss Calculation (All Processes):**
        *   Uses `accelerators["model_a"].accumulate(self.models["model_a"])` context.
        *   Performs forward pass for `model_a` using the original batch.
        *   Calculates `loss_a`.
        *   Calls `accelerators["model_a"].backward(loss_a)` (Accelerate handles scaling and sync).
        *   Uses `accelerators["model_b"].accumulate(self.models["model_b"])` context.
        *   Constructs inputs for `model_b`'s loss calculation (might use original batch or broadcasted generated data depending on the specific algorithm).
        *   Performs forward pass for `model_b`.
        *   Calculates `loss_b`.
        *   Calls `accelerators["model_b"].backward(loss_b)`.
    4.  Returns detached losses.
*   The `train` method handles gradient accumulation checks, optimizer steps (`optimizer.step()`, `optimizer.zero_grad()`), scheduler steps, gradient clipping (`accelerator.clip_grad_norm_`), logging, evaluation triggers, and checkpoint triggers based on the global step.

    outputs_b = self.models["model_b"](**inputs_b)
    loss_b = outputs_b.loss
    self.accelerators["model_b"].backward(loss_b)

**4.4. Weight Synchronization (`_move_model_to_vllm`, `_sync_weights_to_vllm`)**

*   Provides a mechanism (`_move_model_to_vllm`) for the main training process to send updated weights from a training model (`model_a` or `model_b`) to its corresponding vLLM server (`vllm_client_a` or `vllm_client_b`).
*   This method correctly handles DeepSpeed ZeRO-3 by using `deepspeed.zero.GatheredParameters` to ensure parameters are fully available on the main process before sending.
*   It also includes logic to handle PEFT adapters correctly (merging before sending, unmerging after).
*   A helper `_sync_weights_to_vllm` triggers the sync for both models. The frequency of calling this needs to be determined based on the training algorithm.
